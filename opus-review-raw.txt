## Review: CoS v0.5.0 Beta — SQLite WAL State Store + HTML Briefing

I read the five files directly (`state_db.py`, `briefing_renderer.py`, `daily_briefing.py`, `hooks.py`, `schemas.py`), plus the wiring in `briefing_sources.py` and the new contract test (`tests/test_html_briefing.py`), and cross-checked config files (`company.yaml.example`) since the task description referenced options that needed verifying.

---

### BLOCKING

**1. `briefing_sources.py:121-135` (`_calendar_summary`) — the HTML calendar section is dead in production; data-shape mismatch with `briefing_renderer._html_calendar`.**

`_calendar_summary()` is the only place that builds the `calendar_deadlines` entries that reach the real briefing pipeline (`_build_structured_briefing` → `collect_calendar_summary_from_records` → `transform_calendar_events` → `_calendar_summary`). It emits only `{when, summary, event_id, location}`.

But `briefing_renderer._html_calendar()` (lines 464-486) reads `ev.get("start")`, `ev.get("end")`, `ev.get("conference_link")`, `ev.get("event_link")` — none of which `_calendar_summary` ever sets. In the real pipeline every rendered event will show a blank time range (`<span class="ts"> — </span>`) and neither the "Join" nor "View event" button will ever appear, even when the agent-supplied envelope carries `event_link`/`conference_link` per the schema contract added in this same diff.

`tests/test_html_briefing.py` doesn't catch this because it hand-builds a briefing dict with `start`/`end`/`event_link`/`conference_link` directly — it exercises the renderer in isolation, never the real `_build_structured_briefing` → `_calendar_summary` path. So the two halves of "Feature 2" (schema field + renderer) were built to different contracts and were never integration-tested together.

Fix: add `start`, `end`, `event_link`, `conference_link` to `_calendar_summary`'s return dict (pulling from the same event fields `normalize_event` preserves), or change `_html_calendar` to consume `when`/`summary`/`event_id` and drop the mismatched keys. Either way, add one integration test that runs an envelope through `_build_structured_briefing` and asserts the HTML output contains the link.

**2. `skills/daily-briefing/scripts/daily_briefing.py:854-855, 1035-1056` — `--html` and `--output` are parsed but never used.**

```python
run_p.add_argument("--html", action="store_true", ...)          # line 854
run_p.add_argument("--output", dest="output_path", ...)         # line 855
```
`cmd_run()` (lines 1035-1056) only branches on `args.json` / `args.markdown` / else-text — `args.html` is never referenced anywhere in the file (verified via grep), and `args.output_path` is never read, so output always goes to `print()`/stdout regardless of `--output`. Running `daily_briefing.py run --html --output foo.html` silently prints plain text to stdout and ignores both flags.

Additionally, the review brief describes a `delivery.default_format` config option as part of this feature; it does not exist anywhere in the repo (`grep -rn "default_format"` returns nothing, and it's absent from `company.yaml.example`'s `delivery:` block, which only has `channel`/`home_chat_id`/`briefing_time`/etc.). The config-driven default-format behavior described for this release was never implemented.

Fix: in `cmd_run`, add an `elif args.html: rendered = render(briefing, "html")` branch, and if `args.output_path` is set, write `rendered` to that path (creating parent dirs as needed) instead of printing. Either implement `delivery.default_format` or drop it from the release notes.

### MAJOR

**3. `shared/scripts/briefing_renderer.py:453-461` (`_html_pending_approvals`) — mislabels entries by risk level, not action type.**

```python
def _html_pending_approvals(pa: dict) -> str:
    ...
    for action_type, actions in pa.items():
        for a in actions:
            parts.append(f'<div class="item"><strong>{_esc(action_type)}</strong>: ...')
```
This assumes `pa`'s keys are action types (`"mail.send"`, etc.), matching the test fixture. But the real producer, `_build_structured_briefing` in `daily_briefing.py` (lines 964-973), builds `pa_grouped` keyed by **risk level** (`"high"/"medium"/"low"`), the same shape `render_text`/`render_markdown` correctly consume via `pa.get(risk_level, [])`. In production, the HTML section will render `<strong>high</strong>: Send proposal to Acme` instead of `<strong>mail.send</strong>: ...` — plus it silently drops the risk badge that `_html_needs_attention` shows for the same data, so risk color-coding present in every other renderer disappears in the HTML one.

Fix: rewrite `_html_pending_approvals` to iterate risk levels like `render_text`/`render_markdown` do, using `a.get("type")` for the label and `_risk_badge(risk_level)` for the badge.

**4. `shared/scripts/briefing_renderer.py:430-434` (`_link`) — no URL-scheme allowlist; `javascript:` URIs pass through escaped-but-clickable.**

```python
def _link(href: str, label: str, cls: str = "") -> str:
    if not href:
        return ""
    cls_attr = f' class="{cls}"' if cls else ""
    return f'<a href="{_esc(href)}"{cls_attr}>{_esc(label)}</a>'
```
`_esc` HTML-escapes the string but does not validate the scheme. `href` values (`event_link`, `conference_link`, the `link` field on `needs_attention` items) originate from agent-fetched calendar/mail data per the workspace-payload contract in `schemas.py` — i.e., from an external calendar invite or email an attacker can send to the operator. A crafted `conference_link: "javascript:...")` would render as a clickable "Join" button pointing at a `javascript:` URI. Given the review focus explicitly calls out XSS in `render_html`, this is the one HTML-escaping gap: escaping the string doesn't neutralize a dangerous scheme.

Fix: in `_link`, reject/strip hrefs that don't start with `http://` or `https://` (case-insensitive), e.g. `if not re.match(r'^https?://', href, re.I): return ""`.

### MINOR

**5. `shared/scripts/briefing_renderer.py:425-427` (`_esc`) — falsy-but-valid values collapse to empty string.**

```python
def _esc(text: str) -> str:
    import html as _html
    return _html.escape(str(text)) if text else ""
```
`if text` treats `0`, `0.0`, and `False` as absent. `_html_table` (used for the Bookkeeper/Pipeline sections) calls `_esc(item.get(key, ''))` on numeric fields like `amount` or `stale_days` — a record with `amount: 0` or `stale_days: 0` renders as a blank cell instead of "0", which is misleading in a financial/CRM context. Not exploitable, but a real correctness bug for legitimate zero values.

Fix: `return _html.escape(str(text)) if text not in (None, "") else ""`.

### NIT

**6. `hooks.py:696`** — `import re` inside `attachment_drive_suggestion` is redundant; `re` is already imported at module scope (line 12). Harmless but dead weight — drop the local import.

### What looked solid

- `state_db.py`: `_ALLOWED_CAS_COLUMNS` allowlist correctly gates all interpolated column names in `_cas_update` before SQL construction (no injection path found); `_begin_immediate`/`mutate_kv` properly retry-then-raise on `SQLITE_BUSY`/`LOCKED` rather than swallowing; `transition_action`'s `MAX_RETRIES` cap and `_PREVIOUS_STATES` transition table are self-consistent; `cleanup_old_actions` correctly excludes non-terminal states; `_migrate_legacy` is atomic (single transaction per open, so a corrupt legacy file aborts the whole migration rather than partially committing) and idempotent via `migration_log` + `.migrated` renames.
- `hooks.py` `attachment_drive_suggestion`: genuinely read-only — never touches the filesystem or calls a Drive API, only emits a suggestion string requiring explicit user confirmation. Consistent with the "never auto-upload" contract.
- `schemas.py`: `normalize_event`/`normalize_message`/`normalize_file` correctly preserve unlisted optional fields (including `event_link`) via `dict(event)` copy-then-setdefault — the schema layer itself is fine; the break is downstream in `briefing_sources.py` as noted in Blocking #1.
- `render_html`'s empty-briefing and no-JS/inline-CSS-only contracts (tested) hold up on inspection.
